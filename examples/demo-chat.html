单节点聊天室 ​

用 Cherry 引擎构建一个多人聊天室。这是最精简的入门示例，只涉及一个节点、一个业务 Actor，不需要任何外部中间件。

  • 客户端：H5 页面，使用 pomelo-client SDK
  • 连接类型：WebSocket
  • 序列化：JSON（默认是 protobuf，这里为了网页调试方便改成 JSON）
  • 运行模式：Standalone（单节点）

整个服务端只有 3 个文件。

要求 ​

  • Go >= 1.24

获取代码 ​

bash
git clone https://github.com/cherry-game/examples.git
cd examples

启动 ​

bash
cd demo_chat/room
go run .

必须在 demo_chat/room 目录下启动

配置路径（../../config/demo-chat.json）和静态文件路径（../static/）都是相对进程工作目录的。在仓库根目录直接 go run ./demo_chat/room 会找不到配置文件。

启动成功后终端会输出：

Websocket connector listening at Address :34590

服务监听两个端口：

端口协议用途
:34590WebSocket客户端连接
:8081HTTP托管 H5 静态页面

测试 ​

用浏览器打开两个 http://127.0.0.1:8081/ 页面，分别输入昵称登录，然后在文本框输入内容点 send，两个页面都会收到广播。

用 IDE 调试 ​

  • GoLand：打开 demo_chat/room/main.go，直接点 Debug
  • VS Code：左侧栏 运行和调试，选择 demo-chat，点绿色三角

代码结构 ​

demo_chat/
├── room/
│   ├── main.go       入口：创建应用、注册解析器与 Actor
│   ├── actor_room.go 房间 Actor：维护用户列表、广播消息
│   └── protocol.go   消息结构定义
└── static/
    └── index.html    H5 客户端

一条消息的完整旅程 ​

以客户端发一条聊天内容为例，理解这张图就理解了 Cherry 的主干：

浏览器                    解析器 Actor (user)              房间 Actor (room)
  │                             │                              │
  │── ws 连接 ─────────────────▶│  建 Agent
  │                             │  并建一条以 sid 为名的子 actor  │
  │                             │                              │
  │── request room.room.login ─▶│                              │
  │                             │── onDataRoute 路由 ──────────▶│ login()
  │                             │                              │  分配 uid
  │                             │                              │  Bind 到 Agent
  │◀──────── response ──────────│◀─────────────────────────────│
  │                             │                              │
  │── notify room.room.syncMessage ─▶│                          │
  │                             │── onDataRoute 路由 ──────────▶│ syncMessage()
  │                             │                              │  扣余额
  │◀── push onMessage ──────────│◀──── broadcast 给所有人 ──────│
  │◀── push onBalance ──────────│◀──── 只回给发消息的人 ────────│

注意几个关键点：

  1. 客户端连接本身也是一个 Actor。pomelo.NewActor("user") 创建的就是它，每条连接还会以 sid 为名建一个子 actor。
  2. 消息先到解析器，再被路由到业务 Actor。解析器不处理业务，只负责编解码和分发。
  3. 响应和推送是两回事，见下面Response 与 Push一节。

协议一览 ​

客户端与服务端之间只有这几个消息，全部定义在 room/protocol.go：

方向名字类型说明
C → Sroom.room.loginrequest登录，携带昵称
S → C（login 的响应）response{code: 0} 表示成功
C → Sroom.room.syncMessagenotify发一条聊天消息
S → ConNewUserpush有人进入房间（广播）
S → ConMessagepush聊天内容（广播）
S → ConBalancepush余额变化，只发给发消息的人

改协议就是改这里

protocol.go 里的结构体字段名（json:"nickname" 这些 tag）决定了客户端看到的数据格式。改这里等于改客户端协议，两边的改动必须同步。

启动流程 ​

go
func main() {
	app := cherry.Configure(
		"../../config/demo-chat.json", // profile 配置路径
		"room-1",                      // nodeID     节点 id
		true,                          // isFrontend 前端节点才可用 connector
		cherry.Standalone,             // nodeMode   单节点模式
	)

	// 默认序列化是 protobuf，这里改用 json 方便网页调试
	app.SetSerializer(cserializer.NewJSON())

	// 创建 pomelo 解析器
	agentActor := pomelo.NewActor("user")
	agentActor.AddConnector(cconnector.NewWS(":34590"))

	agentActor.SetOnNewAgent(func(newAgent *pomelo.Agent) {
		newAgent.AddOnClose(func(agent *pomelo.Agent) {
			if !agent.IsBind() {
				return
			}
			// 通知 room actor 有玩家断开
			agentActor.Call(".room", "exit", &Int64{Value: agent.UID()})
		})
	})

	agentActor.SetOnDataRoute(onDataRoute)
	app.SetNetParser(agentActor)

	app.AddActors(&actorRoom{})

	httpServerComponent(app) // 用 gin 组件托管 H5 静态页

	app.Startup()
}

cherry.Configure 四个参数是理解 Cherry 的起点：

参数说明
pathprofile 配置文件路径（相对进程工作目录）
nodeID本节点唯一 id，框架靠它从 profile 里查出节点类型、地址、私有配置
isFrontend是否前端节点。只有前端节点能挂 connector 接收客户端连接
nodeModecherry.Standalone 或 cherry.Cluster

路径里的「.room」是什么意思

agentActor.Call(".room", "exit", req) 的 .room 是 Actor 路径，点号前面为空表示「本节点」。

完整写法的路径是 room-1.room（节点id.ActorID）。用 .room 可以避免硬编码节点 id。

消息路由 ​

onDataRoute 决定客户端消息交给哪个 Actor。Pomelo 的 route 字符串是三段式 room.room.login：

段值含义
1roomnodeType，期望由哪种节点处理
2roomhandleName，投给哪个 Actor
3loginmethod，方法名
go
func onDataRoute(agent *pomelo.Agent, route *pmessage.Route, msg *pmessage.Message) {
	// session 是「这一条消息的快照」，不是长连接的状态
	session := agent.NewSession(msg.ID)

	// 登录是唯一允许未绑定 uid 的消息
	if msg.Route == "room.room.login" {
		// 三段式路径：给这个连接对应的子 Actor
		targetPath := cfacade.NewChildPath(agent.NodeID(), route.HandleName(), session.Sid)
		pomelo.LocalDataRoute(agent, route, msg, targetPath)
		return
	}

	if !session.IsBind() {
		agent.ResponseCode(session, ccode.SessionUIDNotBind, true)
		return
	}

	// 两段式路径：给房间 Actor 本身，由它统一广播
	targetPath := cfacade.NewPath(agent.NodeID(), route.HandleName())
	pomelo.LocalDataRoute(agent, route, msg, targetPath)
}

路由的第三段（login）最终会作为 message.FuncName，匹配到 Actor 里注册的 p.Local().Register("login", p.login)。

session 是每消息新建的

从 v1.6.x 起，每条消息都会通过 agent.NewSession(msg.ID) 新建一个 session 快照，里面带着这条连接的 sid / uid 和连接上暂存的键值对。这样做的原因是连接的读写发生在多个 goroutine 上，每消息一份快照可以避免并发读写同一份数据。

也正因为如此，从 v1.6.8 开始 LocalDataRoute 不再接收 session 参数——由函数内部按 msg 构建。

房间 Actor 详解 ​

这是示例的业务核心，逐段看。

结构与 AliasID ​

go
type actorRoom struct {
	cactor.Base
	userMap map[int64]*User // 只被本 Actor 的 goroutine 访问，无需加锁
}

type User struct {
	uid      cfacade.UID
	nickname string
	balance  int64 // 余额，每发一条消息扣 1
	message  int   // 已发送的消息数
}

// AliasID 决定 Actor 路径：room-1.room
func (p *actorRoom) AliasID() string {
	return "room"
}

AliasID() 的返回值就是 Actor 路径的第二段。客户端路由里的 room.room.login 第二段是 room，指的就是这个。

嵌入 cactor.Base 后自动获得 Local() / Remote() / Event() / Timer() / Child() 等能力，只需按需覆写生命周期方法。

OnInit：注册处理函数 ​

go
func (p *actorRoom) OnInit() {
	p.userMap = make(map[int64]*User)

	p.Local().Register("login", p.login)              // 客户端消息走 Local
	p.Local().Register("syncMessage", p.syncMessage)

	p.Remote().Register("exit", p.exit)               // 被 Call 调用走 Remote
}

最容易踩的坑：Local 和 Remote 的区别不是「距离」

Local() 收的是客户端消息被路由过来的请求（走 PostLocal）； Remote() 收的是其它 Actor 用 Call / CallWait 调用的请求（走 PostRemote）。

即使是发给同一个节点的 Call，走的也是 Remote。

所以 main.go 里 agentActor.Call(".room", "exit", req) 注册在 p.Remote() 上，而客户端来的 login 注册在 p.Local() 上。

两端对不上时不会报错，只会「消息发出去了但没人处理」。排查这类问题优先看这里。

OnLocalReceived：控制是否转发给子 Actor ​

go
func (*actorRoom) OnLocalReceived(_ *cfacade.Message) (bool, bool) {
	return false, true
}

两个返回值的含义是 (next, invoke)：

返回值含义
invoke = true在本 Actor 上立即调用注册的处理函数
next = true继续往下走，按路径决定是否转发给子 Actor

这里返回 (false, true) = 「自己处理，不往下转发」。因为聊天室的登录和发言都由房间统一处理，不需要每条连接一个子 Actor。

消息处理函数的签名约定 ​

go
func (p *actorRoom) xxx(session *cproto.Session, req *SomeStruct)
参数说明
第一个（可选）*cproto.Session，会话上下文，框架自动注入
第二个（可选）客户端发来的数据体，框架反序列化后注入

两个参数可以只要其中一个，也可以都要。不必和调用方一一对应 —— 比如 exit 是被 Call 调用的，调用方只带了 uid，所以它只声明一个参数：

go
func (p *actorRoom) exit(req *Int64) {
	if req.Value < 1 {
		return
	}
	delete(p.userMap, req.Value)
}

login：登录与绑定 uid ​

go
func (p *actorRoom) login(session *cproto.Session, req *LoginRequest) {
	// 已经绑定过 uid 说明这条连接登录过了，避免重复建号
	if session.IsBind() {
		return
	}

	// 按 sid 找到这条连接对应的 Agent
	agent, found := pomelo.GetAgentWithSID(session.Sid)
	if !found {
		return
	}

	// 绑定 uid：之后 session.IsBind() 返回 true，也能按 uid 反查连接
	uid := newUID()
	agent.Bind(uid)

	p.userMap[uid] = &User{
		uid:      uid,
		nickname: req.Nickname,
		balance:  1000,
	}

	p.broadcast("onNewUser", &NewUserBroadcast{
		Content: fmt.Sprintf("user join: %+v", req),
	})

	agent.Response(session, &LoginResponse{})
}

Agent 是什么：一条客户端连接在服务端的代表，由 pomelo 解析器管理。可以理解成「能往回推消息、能踢人下线」的那一端。

方法用途
pomelo.GetAgentWithSID(sid)按连接 id 找 Agent
pomelo.GetAgentWithUID(uid)按绑定的 uid 找 Agent
agent.Bind(uid)把 uid 绑定到这条连接
agent.UID()取绑定的 uid

syncMessage：发消息与扣余额 ​

go
func (p *actorRoom) syncMessage(session *cproto.Session, req *SyncMessage) {
	user, found := p.userMap[session.Uid]
	if !found {
		clog.Errorf("user not found: %v", session.Uid)
		return
	}

	user.message++
	user.balance--

	// 广播给所有人
	p.broadcast("onMessage", req)

	// 余额只回给发消息的人自己，所以用 Push 而不是 broadcast
	agent, found := pomelo.GetAgentWithSID(session.Sid)
	if found {
		agent.Push("onBalance", &UserBalanceResponse{CurrentBalance: user.balance})
	}
}

这里能直接读 session.Uid，是因为 login 里已经 Bind 过。如果客户端没登录就发这条消息，onDataRoute 会先把它拦掉。

broadcast：为什么遍历 uid 而不是存 Agent ​

go
func (p *actorRoom) broadcast(route string, v interface{}) {
	for uid := range p.userMap {
		if agent, ok := pomelo.GetAgentWithUID(uid); ok {
			agent.Push(route, v)
		}
	}
}

这里的设计考量

userMap 里存的是 uid 而不是 *Agent，每次广播时再用 uid 反查 Agent。

原因是连接可能断开重连，uid 到连接的映射由框架统一维护更可靠。直接缓存 Agent 指针的话，连接换了一条之后缓存就失效了。

Response 与 Push ​

这两个都往客户端发消息，区别很关键：

ResponsePush
触发前提客户端先发了 request不需要，服务端主动发
是否带 mid带，客户端能对上是哪次请求不带
客户端接收方式写在 pomelo.request 的回调里用 pomelo.on(事件名, fn) 订阅
用途应答某次请求广播、状态变更通知
go
// 应答这次请求（只发给请求方，带 mid）
agent.Response(session, &LoginResponse{})

// 主动推送（不带 mid，客户端按事件名订阅）
agent.Push("onBalance", &UserBalanceResponse{CurrentBalance: user.balance})

例子里的 onNewUser、onMessage、onBalance 都是 push，客户端这样订阅：

js
pomelo.on("onNewUser", function (data) { /* 有人进入房间 */ });
pomelo.on("onMessage", function (data) { /* 收到聊天内容 */ });
pomelo.on("onBalance", function (data) { /* 余额变化 */ });

配置 ​

配置文件在 config/demo-chat.json（下面是节选）：

json
{
    "env": "chat",
    "debug": true,
    "include": ["include/logger.json"],

    "cluster": {
        "discovery": { "mode": "nats" },
        "nats": {
            "master_node_id": "chat-master",
            "address": "nats://127.0.0.1:4222"
        }
    },

    "node": {
        "master": [
            { "enabled": true, "node_id": "chat-master",
              "__settings__": { "ref_logger": "master_log" } }
        ],
        "room": [
            { "enabled": true, "node_id": "room-1", "address": ":34590",
              "__settings__": { "ref_logger": "room_log" } }
        ]
    }
}

启动时传入的 room-1 会被用来在 node 段中查找，匹配到 room 这一组，于是节点类型确定为 room。

Standalone 用不到 NATS

配置里虽然写了 cluster.nats，但 Standalone 模式不会初始化集群组件，所以不需要启动 NATS。这份配置可以直接复制到集群模式使用。

这个示例简化了什么 ​

入门示例刻意省略了一些生产环境必需的东西，迁移到实际项目时要注意：

简化点实际项目应该
newUID 用内存自增用数据库自增、Redis INCR 或雪花算法
用户数据只在内存进程重启即丢失，应落库，见接入数据库
只有一个房间需要多房间时用 room 的子 Actor，每个房间一个实例
没有断线重连客户端需要处理重连与状态恢复
没有鉴权实际项目应有 token 校验，见多节点集群

关于 PacketSpendTime

protocol.go 里有个 PacketSpendTime() 方法，用客户端带来的 PacketTime 减去当前时间，可以粗略衡量一条消息从客户端发出到服务端处理的耗时。做延迟统计时可以用。
